# Seekah 0.38.1 驗證

日期：2026-09-28。package 0.38.1。全部為本機 win32 證據（Windows 11 Home、Node.js 22.23.2），**不是公司 Windows 驗收**。

## 自動測試

- `npm test`：319 項，314 通過、3 略過、2 失敗。兩項失敗與本版無關，是既有的 win32 環境失敗（M26 path coverage、M36 profile chmod），與 0.38.0 相同；不能宣稱全套零失敗。
- 新增 `test/m41.test.ts`：
  - 外鍵索引：以 `PRAGMA foreign_key_list`／`index_list`／`index_info` 檢查 fresh index、舊 index 遷移前與遷移後的所有外鍵，子表欄位都是某個索引的最左欄位（或 rowid）。
  - marker：fresh index 寫入後為 0，`blockIndexCompletedDocuments` 等於文件數。模擬 0.38.0 殘留的 `block_index_1`／`content_storage_2` marker：read-only 開啟不變，writer 開啟後為 0。舊 index 遷移中保留 marker，完成後為 0，之後寫入不再產生 marker。
  - `removeMissing`：刪除 1,100 份（1,050 份 metadata-only、50 份含 heading／content）時分成 1,000／100 兩批，進度為 `write`／「刪除校正」0→1,000→1,100。在第一批後取消：丟出 `OperationCancelledError`，partial 為已刪 1,000 份；再跑一次刪除其餘 100 份，最後各表 row 數與一次刪完完全相同。
  - `sync`：`.localdocsearchignore` 排除 1,050 份後同步，在刪除 1,000 份時取消，partial report 的 `removed` 為 1,000；下次同步刪除其餘 50 份並回報進度。
- 既有測試調整：m24（遷移完成後 marker 由 300 改為 0）、m40（fresh index marker 由 1 改為 0）、m38／m40 的 `removeMissing` 改為 `await`。

## 合成 index：刪除一萬份

20,000 份文件（每 10 份有 1 份含兩個 block），`removeMissing` 刪除其中 10,000 份 metadata-only 文件：1,553 ms，平均每份 0.16 ms（10 批）。

## 真實 store 複本：刪除成本

資料：使用者真實 index 的 0.38.0 備份（240,237 份文件，4.67 GB，含 240,237 筆殘留 marker）。每次各自複製一份，刪除 `C:\Users\mains\AppData` 下依 id 排序的前 2,000 份文件，計時 `IndexStore.removeMissing`（含掃描全部文件路徑）。

| 版本 | 開啟 writer | 刪除 2,000 份 | 平均每份 |
| --- | --- | --- | --- |
| 0.38.0（主目錄 `dist`） | 5 ms | 144,043 ms | 72.0 ms |
| 0.38.1 | 1,016 ms（建立索引、清除 240,237 筆 marker） | 24,045 ms | 12.0 ms |
| 0.38.1，接著刪下一批 2,000 份 | 5 ms | 1,451 ms | 0.73 ms |

- 前 2,000 份中，第 1,001～2,000 份含 316,815 個 block；其他批幾乎沒有 block。刪除成本主要與 block 數成正比（FTS5 `detail=full` rows），0.38.1 約每 block 0.075 ms。
- 在同一份複本逐條計時 0.38.1 的一批 1,000 份 metadata-only 文件：九個 FTS 表、`search_headings`、`documents` 的刪除加上 COMMIT 共約 36 ms，平均每份 0.04 ms。
- 0.38.0 的根因在另一份備份上單獨量測：`DELETE FROM documents` 的 CASCADE 全表掃描 marker，每份 35.9 ms；建立 `index_migration_documents(document_id)` 索引後為 0.1 ms。
- 推估：這次排除的 175,324 份文件共 2,858,823 個 block。0.38.1 約 4 分鐘（block 約 3.5 分鐘，其餘為文件與掃描）；0.38.0 實際在使用者電腦上約 2 小時。

## 未驗證／限制

- 公司 Windows 人工驗收未回報。
- 刪除成本仍與 block 數成正比；刪除大量含正文的文件仍需數分鐘。
- 資料庫檔不會因刪除而縮小；釋放的 page 供之後寫入重用。
- `removeRoot`、`moveRootsToTrash`、`clearDocuments` 仍為單一交易（SPEC §51.3），本版只以補索引降低其成本，未另測真實規模。
- 遷移遇到 SQLITE_BUSY 直接失敗（`database is locked`）不在本版範圍。
