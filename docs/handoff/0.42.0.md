# 0.42.0 交接：搜尋候選延遲載入、局部更新鎖外準備、背景校正批次寫入進度

更新：2026-09-29。package 為 **0.42.0**。

## 範圍

- 行為權威：SPEC §62、§63、§64；決策：D094、D095、D096；流程：D093；驗證：`../0.42.0-VALIDATION.md`。
- 起因：效能審查報告的前三項（P0-1～P0-3），使用者選定後以三條平行分支實作、各自審查再合併。
  - `perf/search-topk`：§62／D094。
  - `perf/lock-free-prepare`：§63／D095。
  - `perf/reconcile-checkpoint`：§64／D096。
- 三項都是純效能改動：搜尋結果、排序、片段、總筆數、索引內容、排除結果與校正完整性語意不變。

## 已完成

- §62 搜尋：候選文件改由 SQL 串流並在 SQLite 端排序，heading／chunk 候選延遲載入，快速模式有界驗證。含補充平面字元（emoji 等）的路徑排序以 metadata `path_order` 旗標決定是否使用 UTF-16 排序鍵；旗標由寫入端維護（`upsert` 與 `touchMetadata`），舊庫只在可寫入連線開啟時偵測一次，唯讀連線缺旗標時保守使用 UTF-16，**不在開啟連線時掃表**。刪除文件不會把旗標降回 native。
- §63 局部更新：穩定等待、讀檔與解析在 writer lock 外進行；每次取鎖一次提交最多 50 份或約 250 ms 的已準備文件，取鎖後逐份重新核對 metadata，改變或消失者不寫入過期內容。同時保留的已準備文字上限 8,000,000 字元。§54 分批規則與 §61 排除規則重用不變。
- §64 背景校正：多個目錄項目的進度合併為一次交易寫入（最多 200 項或距上次提交約 1 秒），目錄處理完成、刪除核對前、校正結束與取消時一定先提交；維持 at-least-once，刪除核對只依已提交的已見項目。
- 測試：m51（等價，以 legacy block 索引為獨立對照）、m52（8 項）、m53（5 項）、m54（3 項）。
- SPEC §62～§64、D094～D096、STATUS、NEXT-TODO、handoff、驗證文件。
- 本批已檢視使用手冊：無使用者可見操作變更，未修改。

## 審查紀錄

- §62 初版每次開啟連線都以 `GLOB` 全表掃描偵測補充平面字元路徑；審查者以 358,124 筆路徑實測約 556 ms／次，會抵銷改善並拉長讀鎖。改為持久化旗標後，32 萬份文件的「唯讀開啟＋第 1 頁」679 → 18 ms。盤點時另補上 `touchMetadata` 漏設旗標。
- §63 初版逐份取鎖，writer 等待大幅下降但湧入時新檔可搜尋延遲與吞吐明顯變差；使用者選擇混合做法（有界群組提交）。另補上不注入 `applyFileUpdate` 的正式路徑測試，涵蓋 §61 排除規則重用與規則檔錯誤。
- §64 初版的時間觸發從整批開始起算，一批超過 1 秒後退化為每項一次交易；改為從上次提交起算。
