# 0.43.0 交接：主索引 WAL、有上限 busy 等待、BUSY／復原固定訊息

更新：2026-09-29。package 為 **0.43.0**。

## 範圍

- 行為權威：SPEC §65、§66、§67；決策：D097、D098、D099；驗證：`../0.43.0-VALIDATION.md`。
- 起因：使用者在公司電腦回報搜尋正常，但工作台一直顯示 `database is locked`。端到端重現（0.42.0）：`/api/search` 全 200，鎖錯誤在 `/api/index-status` 的 `autoupdate.live.recentErrors`（`LIVE_UPDATE_FAILED: database is locked`）。
- 根因：主索引 rollback journal 加 `busy_timeout=0`；搜尋 SHARED lock 擋住背景寫入。
- 本版是儲存／鎖定行為改變，升次版號。不是純效能。

## 已完成

- §65／D097：背景自動更新把主庫 SQLITE_BUSY 當 INDEX_BUSY。持鎖內只做 50／100 ms 短重試；超限停止本輪、已成功者 ack、其餘保留待辦。
- §66／D098：主索引 WAL。readonly 200 ms、constructor／schema 初始化 200 ms、其後寫入 1500 ms。autocheckpoint 約 2 MiB、`journal_size_limit` 4 MiB；每批 PASSIVE，超過 64 MiB 才 RESTART／TRUNCATE；compact 與完整 sync 後強制 truncate。切換 WAL 失敗不使開庫失敗。coordination／lease／queue 仍零等待。
- §67／D099：工作台 HTTP、索引 worker、MCP、TUI、autoupdate CLI／日誌對 busy 與 776／1288／1294 使用固定 `INDEX_BUSY`／`INDEX_RECOVERY_REQUIRED`。
- `isSqliteBusy` 共用判斷（errcode 與精確 `database is locked`／`database table is locked`）。
- `compact` 顯示主庫加 `-wal`／`-shm` 合計；可回收估主庫空洞。
- 測試平台：m26 明確 posix；m36 在 Windows 略過 chmod 拒絕權限斷言（少了一項 Windows 覆蓋）。
- 本批已檢視並更新使用手冊：WAL 附屬檔、整組備份、INDEX_BUSY／INDEX_RECOVERY_REQUIRED、本機磁碟、舊版症狀。

## 審查紀錄

- 初版 `withWriterBackoff` 可能在持鎖下無限重試；改為有限短重試後停輪。
- `9a81171` 誤刪 prepared 路徑「第二次 lstat 檔案已消失則 applyOne／finish」。當時完整套件仍全過。後補回歸並還原刪除路徑（`6201e00`、`0ff3c17`）。
- 工作台與 WAL 測試曾都叫 m56；WAL 改 m58／m59。
- checkpoint 非 busy 錯誤改為 `onWarning` 去重回報，避免默默吞掉。
- 審查與實作分 worktree／分支，合併者統一升版與 STATUS。
