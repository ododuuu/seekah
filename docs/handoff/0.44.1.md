## 審查紀錄與教訓

- **0.44.0 的回歸是漏驗證造成的**：0.44.0 交接文件原本就標明「工作台前端沒有瀏覽器實際畫面檢視」，這個限制真的造成使用者可見的錯誤。**之後任何工作台前端改動，發版前必須跑 `node scripts/ui-smoke.mjs`**（或至少用瀏覽器實際載入）。煙霧腳本已反向驗證能抓到這類錯誤。
- 搜尋加速的審查：(1) `pi3` 靜態審查沒有找到結果語意錯誤，但指出記憶體無上限（極常見詞可能命中數十萬 chunk）、過早建立批次結構、測試缺口（範圍限制組合、restrict、Unicode 門檻、fast total 邊界），皆已修；(2) 主要的批次改動原本沒有反向驗證，已補；(3) 隨機差分測試（650＋30＋6＋2×650）0 差異；`grok` 做到一半因 xAI 額度用完中斷，改由 `pi3` 接手完成。
- 差分測試腳本在 scratchpad（`search-diff.mjs`），不在 repo；若再改搜尋程式，需重建一份等價的新舊比對。
- 整合時 `docs/SPEC.md`、`docs/DECISIONS.md` 各分支都在檔尾追加而衝突；解衝突用「兩邊都留、依編號排序」，並檢查是否出現重複區塊。`D022` 重複是既有問題，不是本批造成。
- 手下的預設工作目錄是主 checkout；每次收件與合併前都對主目錄與各 worktree 做 `git status --short`（本批無越界）。

## 使用者要做的事（部署）

1. 關閉舊的工作台命令視窗，重新雙擊 `seekah-ui.cmd`（舊視窗已載入壞掉的畫面程式）。
2. 在 `C:\Users\mains\seekah` 執行 `npm run build`（若尚未建置）。
3. 啟動背景更新：`.\seekah.cmd autoupdate start`（0.44.0 的檢查點上，舊程序已被停止）。之後用 `autoupdate status` 看「範圍」是否為逐資料夾、不再是 `coarse 句柄=1`，以及待辦數是否下降。
4. 推送：`git -C C:\Users\mains\seekah push origin main`（本機 `main` 領先 GitHub，工作階段讀不到 GitHub 憑證）。
5. 重新索引是可選的：背景更新啟動時會自動做一輪校正（清掉被預設排除的舊索引、補回可能被舊版誤刪的文件）；想立即確定完成再手動 `.\seekah.cmd index`。索引備份在 `%LOCALAPPDATA%\LocalDocSearch-backup-20260930-pre0.44.0\`。
