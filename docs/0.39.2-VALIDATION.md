# Seekah 0.39.2 驗證

日期：2026-09-28。package 0.39.2。全部為本機 win32 證據（Windows 11 Home、Node.js 22.23.2），**不是公司 Windows 驗收**。

## 起因（使用者真實環境）

0.39.1 上線後，使用者 20:35:59 新建 `Desktop\測試用.md`，事件 1 秒內寫入工作佇列，但搜尋不到。工作狀態庫顯示佇列有 2,840 筆待辦，其中 `.codex\.tmp\plugins` 2,492 筆、`.codex\plugins\cache` 255 筆（Codex 12:12–12:35 UTC 解開 plugin）；status 最後局部更新停在 `.codex\.tmp\plugins\...\configuration.md`。逐一「觀察 → 等 1.5 s → 再觀察」估計約 70 分鐘才輪到新檔。

## 自動測試

- `npm test`：338 項，333 通過、3 略過、2 失敗。兩項失敗是既有的 win32 環境失敗（M26 path coverage、M36 profile chmod），與 0.39.1 相同；不能宣稱全套零失敗。
- 新增 `test/m44.test.ts`：
  - 700 個檔案＋1 個最後加入的檔案進入佇列：穩定等待次數在「批數」與「批數 × 3」之間（不是每檔一次），沒有原地退避；每次穩定等待時 writer lock 由本輪持有，輪與輪之間可取得 writer lock；全部檔案與最後一個檔案都可搜尋。
  - 持續變動的檔案：同批的一般檔案在 2 次等待內可搜尋；變動檔案每輪延後，第 6 次（`UNSTABLE_BACKOFF_MS.length + 1`）後確認完成、保留既有索引，佇列清空，沒有錯誤。
- 既有 m11、m37-*、m43、autoupdate 全部通過。實作期間 M11「啟動期間事件在初次同步後觸發一次後續更新」曾失敗：停止發生在觀察階段時批次直接返回、沒有處理已觀察的檔案。改為停止時仍至少處理一個已觀察的檔案（與原本「進行中的檔案完成後才停止」相同）。
- 實作期間曾加入「與索引相同的檔案不等待」，因為會讓事件不再經過 `applyFileUpdate`（M11 依此判斷後續更新）且整批只等一次後效益很小，已移除並同步修正 SPEC §54.2／D085。
