# 0.47 搜尋慢量測筆記

更新：2026-10-02。這是本機 win32 的合成資料量測，不是公司 Windows 驗收，也不是使用者真實索引的量測。

## 執行環境與邊界

- Node.js `v22.23.2`、npm `10.9.8`。
- 所有索引、來源根目錄與 `LOCALDOCSEARCH_DATA_DIR` 都在 `%TEMP%` 下的隔離目錄；沒有讀取或開啟 `%LOCALAPPDATA%\LocalDocSearch*`，沒有啟動使用者 daemon。
- C 的每個 scenario 都重新建立相同合成索引：160 份文件、每份 8 個文字區塊；4 個獨立唯讀搜尋程序同時執行 24 次暖機後取樣，writer 分 48 批、每批 8 次 `upsert`，每批後呼叫產品既有 `checkpointWal()`。
- D 的每個 scenario 都重新建立相同合成索引：20 份文件、每份 768 個區塊；每份文件在開頭與結尾放置兩個查詢詞，其餘為約 620 字元的合成 filler；暖機 1 次後取 5 次當頁 `all-terms` 搜尋。
- 時間是單次本機執行的 p50／p95；背景程序、OS cache、CPU 與其他負載都會影響數字，不能把單次數字當成固定產品承諾。

## C：背景寫入期間搜尋慢

### 基線與候選拆解

| 情境 | 唯讀搜尋 p50 | 唯讀搜尋 p95 | writer commit p50 | writer commit p95 | 結果數 |
|---|---:|---:|---:|---:|---:|
| 無 writer（idle） | 21.4 ms | 27.9 ms | — | — | 160 |
| 產品現況：`mmap_size=1 GiB`、`wal_autocheckpoint` 約 2 MiB | 22.9 ms | 29.2 ms | 4.8 ms | 7.6 ms | 160 |
| 唯讀連線 `mmap_size=0` | 24.7 ms | 34.0 ms | 4.9 ms | 7.9 ms | 160 |
| writer `wal_autocheckpoint=0`，保留產品既有顯式 checkpoint | 22.9 ms | 30.3 ms | 4.8 ms | 7.5 ms | 160 |
| 同時停用 mmap 與 autocheckpoint，仍保留顯式 checkpoint | 22.9 ms | 29.7 ms | 4.8 ms | 7.5 ms | 160 |
| writer 不呼叫顯式 checkpoint（保留自動 checkpoint） | 23.1 ms | 29.0 ms | 4.8 ms | 7.5 ms | 160 |

產品現況相對 idle 的這次合成負載約為 p50 `1.07x`、p95 `1.05x`；沒有重現 NEXT-TODO 所述的 `1.3～1.6x`。停用 mmap 反而較慢；停用自動或顯式 checkpoint 沒有穩定改善。writer 期間所有 reader 都持續得到 160 份結果，沒有 `SQLITE_BUSY`。

### 決定

目前沒有證據把慢化歸因於唯讀連線讀 WAL-index 或 `wal_autocheckpoint`，因此沒有改動 C 的連線設定、WAL 閾值或 checkpoint 策略。這避免用單次、受負載影響的合成結果改變既有鎖等待與 WAL 邊界。`test/m87.test.ts` 保留隔離 WAL 提交期間的讀取正確性回歸，但不把不穩定的毫秒門檻變成產品契約。

## D：長文件多段落完整讀回 blocks

### 前後量測

| 情境 | p50 | p95 | 結果數 | 段落數（首筆） |
|---|---:|---:|---:|---:|
| 修正前：每份文件 `documentBlocks()` 讀完所有 chunks | 93.1 ms | 93.2 ms | 20 | 2 |
| 修正後：以 chunk／heading FTS 保守候選縮小 storage read | 58.0 ms | 65.3 ms | 20 | 2 |

修正後 p50 約為修正前的 `0.62x`，p95 約為 `0.70x`。候選縮小只發生在 current chunk store；block-index／legacy store 仍走原本完整讀取 fallback。內容的 exact matching、每個詞首次命中區塊、相鄰區塊合併、片段產生與結果排序沒有移動到儲存層，也沒有改變 API 欄位或結果選擇邏輯。

`test/m88.test.ts` 以同一批長文件同時跑完整讀取與候選讀取，逐欄比較當頁結果，並要求候選路徑解壓／驗證 chunks 與 bytes 較少。數字是本機 win32 的低負載合成量測；真實文件的區塊大小、查詢詞分布、SQLite cache 與 CPU 負載可能使收益不同。

## 限制與後續證據

- C 未能重現 1.3～1.6 倍，不能宣稱根因已解決；若公司電腦仍觀察到該比例，下一次應加入 event→準備、SQLite transaction、checkpoint、候選驗證與 page materialization 的分段計時，並維持唯讀真實索引探測邊界。
- D 只證明合成長文件在「查詢詞位於少數 chunks」時減少讀取；查詢詞分散到幾乎所有 chunks、FTS 候選接近整份文件或舊索引尚未完成 migration 時，收益可能接近零。
- 所有量測均未寫入產品資料目錄；臨時量測腳本位於 `%TEMP%`，交付只保留本筆記與自動測試。
