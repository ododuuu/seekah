# Seekah 0.39.3 驗證

日期：2026-09-28。package 0.39.3。全部為本機 win32 證據（Windows 11 Home、Node.js 22.23.2），**不是公司 Windows 驗收**。

## 起因（使用者真實環境）

0.39.2 重啟後，背景自動更新從 13:47:47 起超過 5 分鐘停在 `C:\Users\mains\.grok`（666 個檔案、499 MB）的子樹掃描，程序單核 64% CPU；Codex／Grok 同時大量寫入，工作佇列累積到 10,000 筆上限後改記 dirty scope。

## 原因實測

暫存根目錄 `root` 下有 `child\deep`，根目錄非遞迴 watcher、`child` 遞迴 watcher；寫入 `child\a.txt` 與 `child\deep\b.txt`：

- 根目錄 watcher：`change:child`（兩次）。
- `child` watcher：`rename:a.txt`、`change:a.txt`、`rename:deep\b.txt`、`change:deep\b.txt`、`change:deep`。

資料夾的 `change` 與檔案事件重複；0.39.2 以前每個資料夾事件都觸發整個子樹掃描。

## 自動測試

- `npm test`：341 項，336 通過、3 略過、2 失敗。兩項失敗是既有的 win32 環境失敗（M26 path coverage、M36 profile chmod），與 0.39.2 相同；不能宣稱全套零失敗。
- 新增 `test/m45.test.ts`（3 項）：
  - split：直屬子目錄與其下資料夾的 `change` 不寫入佇列、不計入事件、不掃描子樹；同一次變動的檔案事件照常更新。
  - 移入的資料夾（`rename`）仍掃描子樹，其中檔案可搜尋。
  - coarse：資料夾 `change` 同樣忽略。
- 既有 m11、m37-*、m43、m44、autoupdate 全部通過（輪替、處理時間起算點修改後重跑）。

## 實作期間的量測與修正

量測過程中發現兩個 0.39.2 的問題，並否決一個做法（D086）：

1. **持續變動的檔案讓新檔輪不到**：佇列依第一次進入的時間排序，再次變動時保留原時間；每輪 5 s 上限下，持續改寫的檔案一直排在最前面。`scripts/benchmark-autoupdate-dirchange.mjs`（300 個 256 KiB 檔案持續改寫）中，只忽略資料夾事件時新檔 35 s 內不可搜尋。→ 加入輪替。
2. **處理時間上限從本輪開始起算**：事件湧入時主執行緒忙於事件回呼，觀察 500 個檔案要 4–13 s（計時插樁實測），上限用完後每輪只處理 1 份。→ 改從穩定等待之後起算。
3. **否決「同一圈內新進的先處理」**：新筆記 3 s 可搜尋，但湧入期間每輪只處理約 30 份，2,500 檔在 500 s 內未處理完（0.39.2 同條件約 55 s 清空）。

另外，量測腳本原本在同一個程序內寫入湧入檔案，會與監看程序搶主執行緒而扭曲結果；已改為另一個程序寫入。

## 真實 fs.watch 量測（最終版本）

防抖 1,500 ms。舊版為 0.39.2（68e9c5b）。

**大量湧入**（`benchmark-autoupdate-flood.mjs --files 2500`，另一個程序寫入 2,500 個小 Markdown 後新建筆記）：

| | 湧入寫入 | 新檔可搜尋 | 佇列清空 |
|---|---:|---:|---:|
| 0.39.2 | 1.5 s | 46.4 s | 49.9 s |
| 0.39.3 | 2.0 s | 48.6 s | 48.6 s |

兩版相當；每份新文件的解析與寫入約 20 ms，是 2,500 檔約 50 s 的下限。0.39.2 看似較快的逐檔處理，是因為資料夾事件觸發的子樹掃描先把大部分檔案一次索引完（計時插樁：0.39.2 第一輪「觀察」35 s）。

**持續改寫**（`benchmark-autoupdate-dirchange.mjs --seconds 90`，300 個 256 KiB 檔案每 20 ms 改寫一份，第 5 s 新建筆記）：

| | CPU（單核 %） | 新檔可搜尋 | 子樹掃描 |
|---|---:|---:|---:|
| 0.39.2 | 59.0 | 10.1 s | 1 |
| 0.39.3 | 52.2 | 16.2 s | 0 |

這個合成情境中 0.39.2 只做了 1 次子樹掃描且剛好很快，**沒有重現使用者 `.grok` 那種單次掃描數分鐘的情況**；0.39.3 的效益（不再做重複的子樹掃描）由自動測試與原因實測支持，實際改善幅度要在使用者環境確認。
