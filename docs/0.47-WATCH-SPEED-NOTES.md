# 0.47 watcher 速度量測筆記

## 範圍

本次只處理使用者指定的 A、B：

- A：把 watcher 更新拆成事件→排程、穩定等待、列舉、取鎖、提交五段，將最近一次量測留在 `autoupdate status`／API 的 root 狀態中。
- B：每個局部批次的檔案各自以事件落點計算穩定等待；穩定等待 Promise 在處理候選檔案前一起啟動，解析／準備前一檔時不持有 writer lock，後續檔案的 metadata 等待可與處理重疊。

背景寫入期間搜尋變慢的 C 已依使用者最新指示重新分配。本分支沒有執行 C benchmark，沒有形成 C 結論，也沒有可移交的 C 發現；不新增 SPEC §90 或 D122。先前被拒絕的 mtime 排序與 recent-files local queue 實驗也沒有重跑。

## 條件與限制

- Node `v22.23.2`、`win32`，使用本機暫存目錄與明確指定的暫存 IndexStore；沒有讀寫 `%LOCALAPPDATA%\LocalDocSearch*`。
- 測試資料是合成文字檔；real watcher 量測使用實際 `fs.watch`，synthetic 量測使用測試用 watcher。
- 以下數字是單一工作站、短檔案、空閒索引的診斷量測，不是完成時間承諾，也不是公司 Windows 驗收。

## A/B 前基線

A/B 前的合成資料／實際 `fs.watch` 量測使用 1,500 ms debounce 與整批一次穩定等待：

| 情境 | 觀察值 |
| --- | --- |
| 安靜單檔，3 次 | 寫入→watch callback `2.53–2.60 ms`；事件→開始 updating `1,525–1,533 ms`；寫入→可搜尋 `3,048.5–3,074.2 ms`；sleep `1,500 ms` |
| 400 次寫入 | 目標檔寫入→事件 `2.375 ms`；寫入→可搜尋 `3,967.3 ms`；事件計數 `363`；佇列 `405`；sleep `1,500 ms` |

400 次寫入的事件計數低於寫入次數只能證明這次測量觀察到事件合併／遺失現象，不能單獨判定根因；因此沒有加入未被量測支持的事件重試或 recent-files queue 修正。

## A/B 後量測

A 的分段量測由 `m85` synthetic 與 real `fs.watch` 測試覆蓋。額外用同一份暫存資料量測三次；real watcher 維持 1,500 ms debounce，synthetic watcher 使用 200 ms debounce：

| 情境 | 寫入→事件 | 寫入→可搜尋 | 最近一次分段量測（ms） |
| --- | ---: | ---: | --- |
| synthetic，3 次 | `0.7–0.8 ms` | `231.1–235.5 ms` | 事件→排程 `3.70–5.32`；穩定 `198.37–202.08`；列舉 `6.14–6.64`；取鎖 `0.98–1.08`；提交 `5.50–7.94` |
| real `fs.watch`，3 次 | `0.9–1.5 ms` | `1,519.7–1,533.6 ms` | 事件→排程 `1,505.14–1,515.43`；穩定 `0.01`；列舉 `0.31–1.60`；取鎖 `0.97–1.02`；提交 `5.71–8.37` |

在這個單檔條件下，B 讓穩定等待從排程後的額外 1,500 ms 變成事件落點已經消耗的等待，因此 real `fs.watch` 的寫入→搜尋約由 `3.05 s` 降到 `1.52 s`。這只證明此測試路徑的等待重疊有效，不證明原始約 10 秒現象的唯一根因是穩定等待。

B 的 m86 正向測試先阻住第一檔解析，再驗證第二檔的穩定等待已開始；移除預先啟動的穩定等待後，反向執行觀察到 `sleepCalls` 為 `1` 而非預期 `2`，測試失敗，恢復後通過。m44 的兩個既有局部批次／持續變動測試也通過，包含不持有 writer lock 與持續變動檔案延後處理。

## 結論

- A 提供可由 status／API 讀取的瓶頸分段證據；目前沒有足夠證據宣稱已修復 watcher 漏事件根因。
- B 以 `stableSince` 保留每檔事件落點，先啟動候選檔案的穩定等待，再依序解析／準備／提交；穩定等待期間不取 writer lock。
- 僅以本筆記數字無法外推公司 Windows、長時間高負載、同步寫入或大量檔案 burst 的結果，仍需依後續專案驗收條件測試。
