## 已合併內容

### SQLite 錯誤邊界與背景更新啟動降級：`fix/robust-errors-49`

- 對應 SPEC §§101–102、D137–D138、`m97.test.ts`～`m98.test.ts`。
- `compact` 遇 SQLite busy／locked 時分類為固定 `INDEX_BUSY`，不把 `SQLITE_BUSY` 原文交給使用者；recovery 類沿用固定 recovery 訊息與退出碼。
- `rememberError` 對 busy／recovery 錯誤使用固定分類，避免 live status／log 保存 SQLite 原文；其他錯誤仍保留原本的錯誤語意。
- `cleanupOrphanRoots` 是啟動時的 best-effort 整理；清理失敗會記錄後讓 engine 降級並繼續建立 watcher／consumer，下一次啟動再試，不吞掉主索引或同步資料完整性錯誤。
- `pi3` 補強 m97／m98 的 busy、recovery、cleanup failure 與反向契約測試。

### 工作台容量、MCP explain_path 與 Windows 路徑正規化：`fix/status-mcp-49`

- 對應 SPEC §§103–105、D139–D141、`m99.test.ts`～`m101.test.ts`。
- Workbench `/api/index-status` 與設定頁顯示索引檔案容量、SQLite `-wal`／`-shm`／journal 及既有 sidecar metadata，沿用 CLI 的 storage footprint 計算。
- stdio MCP `explain_path` 維持 tokenless，但只回查詢中的單一 root／path 結果，不列出其他根目錄或 arbitrary read 資訊。
- Windows 8.3 短名與 `subst` alias 先正規化，再判斷預設排除與 volume root；不改登錄 root 或索引 path。
- `DECISIONS.md` 維持 D144 起由新到舊排列。

### fs.watch 壓力驗證與匿名診斷：`research/watch-miss-49`

- 對應 SPEC §§106–107、D142–D143、`m102.test.ts`～`m103.test.ts`。
- 14 個真實 `fs.watch` 合成壓力情境共核對 626 份 synthetic token，`search()` 可搜尋集合遺失 0；這一輪未重現漏事件，不能據此宣稱底層根因已解決。
- 觀察到某輪 `stable wait` 約 16 秒；量測受檔案數、解析器、磁碟與負載影響，不是固定 SLA。
- 新增 `seekah autoupdate diagnose`。輸出以 live snapshot 登錄順序使用 `R1`、`R2`……及相對深度，不輸出根目錄／子目錄路徑、檔名或雜湊；命令只讀取 live daemon，不自行啟動或停止背景更新。

### CLI 狀態 JSON：`feat/status-json-49`

- 對應 SPEC §108、D144、`m104.test.ts`。
- `status --json` 與 `autoupdate status --json` 提供腳本使用的結構化輸出，頂層含 `schemaVersion: 1`；未指定 `--json` 時的人類輸出與既有退出碼語意維持不變。
- JSON 契約允許新增欄位，禁止刪除、改名、改型別或改變既有欄位意義而不升版。

## 誠實限制與待使用者觀察

- 監看漏事件根因仍未證實。m102 的 14 情境、626 份 synthetic token 遺失 0 只代表該輪沒有重現，不代表 Windows `fs.watch` 在所有拓撲與負載下不會漏事件。
- 若要取得實際背景更新資料，使用者必須先重啟背景更新，再執行 `seekah autoupdate diagnose`，回傳其匿名摘要與 timing；不要用一次合成通過替代使用者環境證據。
- `autoupdate.log` 仍可能記錄完整路徑。這是本機檔案的既有診斷內容，與 `autoupdate diagnose` 的匿名、不含路徑或雜湊輸出是不同邊界；不要把 log 外傳。
- `stable wait` 的 16 秒觀察值受負載影響，不是完成時間承諾；需依 diagnose 的實際 `lastTiming` 判讀。
- 本版沒有公司 Windows 使用者回報；不得宣稱公司 Windows 0.49.0 驗收通過。

## 部署與下一步

1. 在本機執行 `npm ci` 與 `npm run build`，再依產品入口啟動 Seekah；不要刪除、搬移或重建既有 LocalDocSearch 資料目錄。
2. 需要腳本整合時使用 `status --json` 或 `autoupdate status --json`，先檢查 `schemaVersion`，並忽略未認識的新欄位。
3. 若懷疑監看漏事件，重啟背景更新後執行 `seekah autoupdate diagnose`，回傳匿名輸出與 timing；同時保留 `autoupdate.log` 在本機，不要上傳完整路徑。
4. 若 JSON 欄位需要刪除、改名、改型別或改語意，先新增 SPEC／DECISIONS 並升級 schema／版本，不直接修改既有契約。
