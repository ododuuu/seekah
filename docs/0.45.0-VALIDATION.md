## §79／D111 Toggle Switch 與「背景更新關不掉」（`test/m75.test.ts`）

- 現象（使用者回報）：背景索引開了之後好像無法從 UI 關掉；且應為 Toggle Switch 而非 checkbox。
- 監工先用隔離暫存索引驗證 API 層：`POST /api/settings` 送 `autoupdateEnabled` 開、關都正常（開啟後 `mode=background`，關閉後停止）。所以問題在 UI 層。
- **根因**：畫面狀態在儲存後等待 `refreshStatus()`，而 `GET /api/index-status` 在真實大索引上約 2 秒，慢速或過期的回應會把剛成功的新狀態蓋回舊值，看起來像是關不掉或彈回去。
- 修正：設定頁四個布林控制（刪除確認、精確總數、背景自動更新、登入時啟動）改為 `button role="switch"`＋`aria-checked`，可鍵盤操作，旁有「已開啟／已關閉／處理中…」；POST 回應直接作為狀態來源，`statusRevision` 保護慢速／過期回應；失敗回復並顯示明確錯誤。
- 煙霧測試涵蓋：滑鼠開／關／再開、Enter／Space、aria 與 API 一致、慢速 `index-status` 不回彈、POST 失敗回復、登入啟動與背景更新分離、CLI `autoupdate start` 後由 UI 關閉、前景 `watch` 拒絕遠端關閉並顯示明確錯誤、索引進行中仍可切換。
- 反向驗證：移除 switch role 或 stale guard 都會被契約測試偵測。

## §81／D113 背景更新開機補捉與工作台開啟提醒（`test/m77.test.ts`）

- 需求（使用者）：初始化索引完、關掉 UI 與終端、下次打開，希望自動更新關閉期間的變更；或打開時提醒並給按鈕，也可選擇關閉。
- 設計：兩個獨立的三態設定（`ask`／`auto`／`off`），存在索引 metadata：
  - `startupCatchupMode`（背景更新程序啟動時，如何處理停止期間留下的 downtime gap）：預設 `auto`（維持既有「啟動後校正」行為）；`ask` 由使用者在工作台提醒中按「立即補捉／稍後提醒／略過本次／關閉開機補捉」；`off` 略過整根校正但仍處理已落盤的明確事件。
  - `workbenchOpenMode`（開啟工作台時，若背景更新**沒有在執行**）：**預設 `ask`（新舊索引皆是）**；`ask` 顯示提醒列，四個動作「開啟背景更新並補上遺漏」「只做一次完整校正」「稍後再說」「不再提醒」；`auto` 自動啟動背景更新並顯示通知，該次啟動直接補捉、不再二次詢問；`off` 不處理。整顆磁碟根目錄時提醒列加註可能耗時與資源。兩種提醒互斥，不重複打擾。
- **硬性規則與驗證**：使用者沒有明確選 `auto` 時，不得自動啟動任何程序；伺服器端在自動啟動前再次讀取設定確認，不只靠前端判斷。測試有明確反向斷言「`ask` 與 `off` 不得啟動 daemon」。
- **審查事件**：手下第一版只做了 `startupCatchupMode`（daemon 已在跑時的 gap 策略），沒有涵蓋使用者的原始情境（開啟時背景更新根本沒在跑，例如重開機後）。監工驗收時發現並退回，補上 `workbenchOpenMode` 與提醒列。
- 驗證：M77 8 項（metadata 往返、預設 ask、三態行為、auto 單次啟動、ask／off 不啟動、daemon ask／auto／off runtime）；煙霧測試兩種視窗涵蓋提醒列四動作與各按鈕行為、auto 自動啟動與通知、off 無提醒、背景更新已在跑時無新提醒、「不再提醒」後設定為 off 並可於設定恢復、設定保存失敗回復。
