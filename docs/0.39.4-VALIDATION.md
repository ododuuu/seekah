# Seekah 0.39.4 驗證

日期：2026-09-28。package 0.39.4。全部為本機 win32 證據（Windows 11 Home、Node.js 22.23.2），**不是公司 Windows 驗收**。

## 自動測試

- `npm test`：345 項，340 通過、3 略過、2 失敗。兩項失敗是既有的 win32 環境失敗（M26 path coverage、M36 profile chmod），與 0.39.3 相同；不能宣稱全套零失敗。
- 新增 `test/m46.test.ts`（4 項，測試把每輪展開上限調為 60）：
  - 大資料夾（240 個檔案、4 個子資料夾）：第一輪佇列不超過上限＋1、資料夾待辦尚未確認；展開中新建的檔案在 2 輪內可搜尋且當時資料夾仍未展開完；最後全部可搜尋、佇列清空、沒有呼叫整棵同步、展開只計一次。
  - 展開略過被排除的資料夾（`cache/`）、`node_modules` 與連結（junction）。
  - 刪除核對：資料夾內刪除一個舊檔、新增一個檔案後以 `rename` 事件展開：舊檔從索引移除、子資料夾內仍存在的檔案保留、新檔可搜尋。
  - 佇列來源：`expand` 後收到 `event` 升為事件；`event` 後被展開不降級。
- m37-scope「未知 filename 只補掃子範圍」「新直屬資料夾 attach 後掃描」與 m45「移入資料夾」改為檢查展開結果（內容可搜尋、`subtreeScanCount`、不呼叫整棵同步），並以假計時器驅動多輪。
- 實作期間發現並修正：
  - 展開寫入待辦後沒有排下一輪，檔案待辦沒人處理（測試逾時抓到）。
  - 上限只在換資料夾時檢查，單一資料夾的整份清單一次讀完；改為讀到一半的清單保留到下一輪。
  - 展開出來的待辦與事件待辦同樣先進先出時，移入的大量檔案會排在之後新建的檔案前面；改為事件待辦優先。
- 未涵蓋：展開中有讀取失敗時不做刪除核對（Windows 上難以穩定製造不可讀子目錄）。

## 真實 fs.watch 量測

`node scripts/benchmark-autoupdate-movein.mjs [--dist <dist>] --files 600 --kib 700`

在監看範圍外準備 600 個 Markdown（6 個子資料夾、共約 420 MB，規模類似使用者的 `.grok`），以 `rename` 移入 `tool\bundle`，1 秒後新建 `Desktop\新筆記.md`。防抖 1,500 ms。舊版為 0.39.2（68e9c5b）。

| | 新筆記可搜尋 | 整個資料夾可搜尋 | 子樹掃描 | 局部更新 |
|---|---:|---:|---:|---:|
| 0.39.2 | 112.6 s | 117.2 s | 9 | 1 |
| 0.39.4 | **4.4 s** | 211.3 s | 1 | 601 |

- 新檔案不再被移入的大資料夾擋住（約 25 倍）。
- 代價：整個資料夾處理完的時間約 1.8 倍。逐檔處理時每輪有 1.5 s 穩定等待、處理 5 s，約四分之一的時間在等待；整棵同步則連續處理。
- 0.39.2 對同一次移入做了 9 次子樹掃描，與 0.39.3 找到的資料夾事件重複問題一致。
