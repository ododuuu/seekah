**量化讀取來源**

- `測試`：107 個實際正文文件完整讀 2,601 payload，2 個 filename-only 文件不讀正文；第一頁 20 結果中 18 個正文 snippet 各重讀 1 payload。因此 `2,601 + 18 = 2,619`，unique 2,601、duplicate 18，全為分頁重讀，不是 owning-block expansion。ranking 本身沒有 payload-level pruning。
- `SPEC.md`：4,954 summary → 4,640 Bloom ordinals，其中 33 個屬於 filename-only、generator 未消費；實際 seed 4,607 + reconstruction 31 = 4,638。38 個 filename-only 文件不讀正文，第一頁全部檔名命中，snippet payload reads=0；full fallback=0、duplicate=0。
- 稀有查詢：2 個候選共 461 summary，Bloom 已選 460；重建加 1、分頁再讀 1，合計 462。只有兩個文件並不保證快：其中一份已選 449／450 payload，重建只補 1。

**Block expansion 不是這兩筆 trace 的主要放大器**

- `SPEC.md` 加權 expansion ratio 1.006729×，最大單 pass 1.1×，最多單 pass 多讀 18 payload；largest pass 575→593。47 份多 payload 文件讀到至少 90% 正文，但這 47 份在重建前的 Bloom ordinal 已經達到 90%，不是 reconstruction 才推成近全文。
- `測試` ranking 全部為 full fallback；其 ratio=1 只來自 18 次 snippet mapping，不能解讀成 posting payload expansion。最大單文件 825 payload。
- 全庫 5,313,248 blocks，786 個跨多 payload；最大 block 跨 182 payload，5 個跨至少 100。實際 `SPEC.md`／稀有查詢候選確實有 span=182 的 block，但不能只因存在大 block 就把 4,638 次讀取歸因於 expansion。`測試` 候選最大 span=32。
- filename 命中直接跳過 blocks generator；heading 命中則不是 metadata-only shortcut，ranking 仍消費 generator；payload Bloom 只存正文，heading-only／空 payload 候選可能保守 full fallback。此處說明 code path，不冒稱本次慢查詢有該 fallback（`SPEC.md` 實測為 0）。

**payloadLookup 真正做了什麼**

| SPEC.md 的 lookup 子項 | execute 次數 | prepare ms | execute ms |
|---|---:|---:|---:|
| 全文件 blocks metadata（1,652,374 rows） | 106 | 4.043 | 3,930.922 |
| seed payload→owning block IDs（1,442,468 rows） | 106 | 4.618 | 1,500.584 |
| blob 查詢，含反向 mapping 子查詢 | 106 | 6.279 | 1,011.776 |

SQL 加 prepare 為 6,458.222 ms；其餘 lookup 約 435.418 ms 包含 JSON／Set 建立與診斷計數，不含解壓。`.all()` 的 execute time 包含 SQLite、native→JS rows／blob 搬移，沒有再細分磁碟 I/O 與 copy，不能把它全稱為磁碟時間。沒有 async／yield 等待、每 payload SELECT 或顯式讀取 transaction；busy timeout=0，不代表排除 OS／背景 writer 負載。metadata Map 與 fragment reconstruction 在 lookup 計時之外，歸 exact self。

現況是 per-document 查詢模式：每個 filtered stream 三條 SQL（metadata、mapping、blob），不是每 payload 三條。全文件 stream 兩條；snippet 另有 block id 與 mapping 查詢，再走 stream。既有 payload SQL 已使用 `document_id` 與 `ordinal IN (...)`，不是尚未 batching 的逐 payload SELECT。

EXPLAIN 顯示 mapping 前向查詢使用 `document_payload_blocks_document_block (document_id=?)`，反向子查詢用 covering primary key `(document_id=?)`，兩者都不是以第二欄作點查找；外層 blob 才是 `(document_id=? AND ordinal=?)`。查詢會掃該文件 mapping 範圍再篩選；不能僅靠批次 blob retrieval 消除 metadata／mapping 的百萬 rows materialization。

**解壓與 exact self**

- `SPEC.md` 的 2,579.600 ms 包含 Brotli 1,289.164 ms、UTF-8 decode＋JSON.parse 1,290.437 ms；不是純 Brotli。共處理 285,103,909 解壓 bytes，原 trace 的 4.56 秒沒有子計時，不能宣稱全部由 payload 數量造成。
- exact inclusive 14,433.344 = lookup 6,893.641 + decode/decompress 2,579.600 + self 4,960.103 ms。self 中 block 文字正規化／比對 2,174.448 ms；餘下約 2,785.655 ms 包含 Map、block 重建、迴圈與 instrumentation，尚未獨立 CPU 歸因，不冒稱純 includes。`測試` 的頁面回讀在 exact 之外，不能拿全搜尋 lookup/decompress 硬扣 exact inclusive。

**歷史提案（第 1 項已於本批實作）**

1. 優先降低 metadata／mapping materialization 與每份文件反覆掃描：先 prototype lookup plan／必要 metadata 取用，保持完整 block、heading、排序與跨 payload 正確性。`SPEC.md` metadata＋mapping execute 已佔約 5.43 秒，但不能把這個時間全部當可省。
2. 改善既有 payload Bloom 選擇性／短詞候選方式：目前三字以上是任一 trigram 通過，兩字完整 fallback；稀有查詢仍近全文。不得直接改成所有 trigram 必須同 payload，會漏跨界片語；不新增索引，實作前需另核准 correctness 方案。
3. statement reuse／跨文件 batch：prepare 僅約 15 ms；不是首要槓桿。既有 blob 已按文件 batch，變更 SQL 應以計畫與 row volume 驗證，而非假設 4,638 個 round trips。
4. 消除分頁重讀／有界快取：對 `測試` 只影響 18 payload，`SPEC.md` 為 0，效益有限且增加 memory／index version 一致性風險。
5. 解壓／decode 與 exact 正規化：可再 profile CPU、減少資料處理量；不要直接截斷大 block 或限制 expansion，這兩筆不是 expansion explosion，且任意上限會造成 false negative。
